D405 color sequence 614 and its exact timestamp appeared twice; depth advanced

rule was relaxed. Earlier failures retained source traces and completed files.
The original diagnostic's `frames: 0` on failure is its default summary value,
not evidence of receiving zero physical frames; its partial log contains data.

## Initial conclusion and next test (before cable bypass)

Repeated failure without the writer, with the older diagnostic implementation,
and with D405 as the only active device narrows the fault to the D405 acquisition
path. It does not prove whether the cause is the extension chain, host USB port,
SDK/firmware or camera. Physical USB packet loss has not been directly measured;
kernel logs were unavailable to the unprivileged operator. Do not describe the
extension hardware as the confirmed root cause.

The user states that a direct-cable comparison is possible later, but currently
there is no sufficiently long cable. Preserve the current results and stop
capture until that comparison is possible. Resume as follows:

1. Keep the software/image/profile unchanged and bypass the D405 extension chain

   followed by all three cameras without encoding, and compare counters/timing.
2. If source stability passes, run the existing hardware shadow smoke and one
   40-second recording. Recheck matching statistics and real depth/codec load.
3. Confirm actual third-view roles before claiming semantic binding acceptance.
   Then run the full 20 x 40-second batch and separate interrupt/disconnect tests.
4. If direct D405 still fails, investigate only the implicated SDK/device path;
   the passed software baseline does not require blanket retesting.

Common-clock accuracy, startup matching behavior, actual scene-quality review,
full-batch cost, and physical fault/recovery acceptance remain unresolved. These
results do not establish full M07/M08/M11/M13 hardware acceptance.
