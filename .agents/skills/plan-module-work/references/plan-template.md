# MXX: Feature or Module Title

> **Code style requirement: Economical code, exceptional readability, and excellent abstraction design.**

- Module: MXX and the name from the meta plan
- Status: draft
- Parent: relative link to the repository meta plan
- Updated: date
- Dependencies: module IDs and relevant formal plans
- User alignment: pending; replace with the actual date and agreed scope when aligned

## Problem and Intended Behavior

Explain the concrete need and observable result. Distinguish confirmed requirements from proposals.

## Scope and Non-goals

Define the change and its boundaries. Identify decisions still needed before implementation.

## Design and Interfaces

Describe module responsibilities, data/control flow, interface semantics, units, failure handling, and deployment or hardware constraints relevant to this work. Keep detail proportional to the change.

## Implementation Steps

List the ordered work and dependency gates. Explain how the implementation will remain economical, readable, and well abstracted; do not restate generic engineering slogans in place of a design.

## Acceptance Plan

Reuse the meta plan's MXX-Axx IDs. Add stable suffixes for detailed cases without changing the parent case's meaning.

| Case ID | Behavior and pass criterion | Environment / motion required | Verification procedure |
| --- | --- | --- | --- |
| MXX-Axx | Define the observable criterion | Software, camera-only shadow, or real robot | Define a reproducible procedure |

## Alignment Record

Record actual user agreement, its scope, and any material revisions. Until agreement exists, leave this section explicitly pending.

## Implementation and Validation Results

Before implementation, state: **Not implemented. No checks have been run for this plan.** Replace this sentence with factual results as work proceeds.

| Date / revision | Case ID | Environment and command or procedure | Result | Conclusion / artifact |
| --- | --- | --- | --- | --- |

Results use PASS, FAIL, NOT RUN, or BLOCKED. Include actual relevant versions; unknown values remain unknown. Separate software success from hardware acceptance.

## Remaining Work and Acceptance Conclusion

State whether the agreed behavior is accepted, awaiting acceptance, or blocked. List unresolved cases, limitations, and the next concrete action. Never turn unrun tests into an acceptance claim.
